# P04 本地状态性能基线

时间：2026-09-12 23:20:53（Asia/Shanghai）。对象：1.2.146 的当前未提交工作区。这里只交付量测，没有修改 usage、session、API ledger 的业务算法，也不代表安装版已经优化。

## 结论

在这台机器的合成数据中，真正需要优先处理的是同步扫描及整份账本写入，不是所有轮询都慢：

- 2000 会话首次 usage 同步耗时 3.87–5.96 秒，并产生近乎同长度的事件循环阻塞。
- 即使没有新增记录，到期 usage 扫描仍耗时 184–523 毫秒；只做元数据扫描，没有读取正文或写账本。两秒缓存内空轮询约 0.01 毫秒。
- 100 账号、365 天聚合账本新增一条 204 字节事件，仍写出 13.67 MiB 完整 usage 快照；此次耗时 406 毫秒。
- API 总明细达到 20000 条时，每记录一个请求重写约 7.66–7.79 MiB，耗时 52–54 毫秒。即使这 20000 条分散在 100 个 Key 上，整份写入量也没有减少。
- 2000 会话的后台暖扫描耗时 599–884 毫秒，但主要使用异步文件读取，事件循环最大观测延迟约 39–41 毫秒；HTTP `/api/sessions` 对应的纯快照及序列化仅约 7–9 毫秒。

以上是模块基线，不是 HTTP 端到端延迟，也不是“账号越多就必然更慢”的证明。同机后台负载与系统文件缓存造成明显波动，20 账号的一些结果反而比 100 账号更慢。

## 方法与数据规模

脚本：[benchmark-local-state.js](../scripts/benchmark-local-state.js)。完整原始结果：[PERFORMANCE-BASELINE-2026-09-12.json](PERFORMANCE-BASELINE-2026-09-12.json)。

运行方式：在仓库目录运行 `node scripts/benchmark-local-state.js`；`--quick` 只运行 1 账号、普通规模，用于验证隔离脚本。进度写 stderr，结构化结果写 stdout。

两组独立矩阵，不将所有维度混成一个未经解释的 HTTP 请求：

| 矩阵 | 账号/Key | 普通规模 | 大规模 |
| --- | --- | --- | --- |
| 会话＋usage | 1、20、100 账号 | 总共 20 会话、7 天历史聚合桶 | 总共 2000 会话、365 天历史聚合桶 |
| API ledger | 1、20、100 Key，每 Key 对应合成账号 | 总共 100 条明细 | 总共 20000 条明细，均摊到 Key；不是每 Key 20000 条 |

每个会话包含 4 条唯一 token 事件，采用真实 JSONL 解析和真实文件目录枚举。usage 冷同步后验证全部 `会话数 × 4` 条事件已入账。随后补入对应天数的合成聚合桶，用于暖扫描、汇总和单增量写入。冷同步不包含这些历史聚合桶的首次读取。

会话模块使用真实 `state_5.sqlite` 合成目录、名称索引、全局状态文件和 JSONL。为了让同一套多账号 fixtures 被同一次真实递归扫描覆盖，将该实例的扫描根指向专属合成账号目录；不修改生产模块。2000 个文件仍遵守现有最多 400 个近期 rollout 保留上限，脚本断言结果数符合此上限。这不是 2000 个会话同时解析/显示的基准。

API 模块使用真实构造器、`recordUsage`、`publicState`，并从 server 源码只提取 `readJson/writeJsonAtomic` 两个函数，不执行 server 初始化。明细是合成记录，汇总字段由构造器归一化；该组用于序列化与写放大量测，不用于账本金额、幂等性或历史对账验收。

首次同步、首次会话扫描和单增量各测 1 次；暖路径及 API 路径各测 3 次，表中是中位数，首次路径是单样本。这里的“冷”仅表示新模块实例/空游标，文件刚由脚本创建，系统缓存未清空，因此不是磁盘冷缓存。

计数覆盖 JS 层成功的正文读写、打开/关闭/目录/状态等元数据调用，不含 SQLite 原生层读取及 OS 缓存。`readFileSync` 内部嵌套读不会重复计字节；异步 `FileHandle.read` 按实际 bytesRead 计量。CPU 是进程 user+system 累积时间，不等于主线程独占 CPU；Windows 计时粒度下短操作记录为 0，不代表完全不消耗 CPU。

缓存内 `sync()` 三组普通规模中位数 0.011–0.018 毫秒，大规模 0.012–0.013 毫秒，均无 JS 文件读写。它只代表缓存门控本身；实际 `/api/usage` 仍另做 summary 和响应序列化，bootstrap/floating 还有其他业务。

## 调用链与建议顺序

1. `/api/usage`、bootstrap、floating 都可能进入 `CodexUsageTracker.sync()`；其全目录同步扫描、每个新文件查找旧游标路径，以及完整 JSON save 是优先对象。应先建立按文件身份索引和增量失效机制，再考虑后台分段/异步处理，保留断点、截断检测、归属和去重语义。不能单纯扩大两秒缓存把额度或用量长期延迟。
2. 会话接口已读内存；优化重点应放在后台 `scan()` 的索引/目录版本缓存、枚举范围及数据库查询，而不是只降低 `/api/sessions` 的频率。首次/暖扫描耗时长不等于整个期间都阻塞主线程。
3. API `recordUsage()` 的成本主要受所有 Key 的合并快照规模影响。后续若改存储事务或批量持久化，必须保持“明细证据与累计值同一次提交”的现有一致性，不可为减少写入直接截断、分成无事务双文件，或丢弃历史。
4. 下一轮可用同脚本建立优化前后差值，并增加独占机器重复、首次磁盘冷读、大单文件、真实只读脱敏样本和完整 HTTP 并发压力。暂不据此制定跨机器绝对 SLA。

本轮仅完成性能基线与可重复脚本；上述性能代码调整、真实场景端到端验收、打包和发布均未执行。
