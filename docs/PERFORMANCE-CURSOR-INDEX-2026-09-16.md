# P04 补充：用量游标索引优化

本次只消除新文件/已移动文件查找旧游标时的全表重复枚举，不更改定价、token 统计、持久化事务、缓存时间或 UI。原基线见 `PERFORMANCE-BASELINE-2026-09-12.md`；这份记录是一个小范围改进的验收，不代表 P04 全部性能问题已解决。

## 修改与不变量

`lib/codex-usage.js` 原先每遇到一个新路径，就 `Object.keys(cursors).find(...)`，对所有无关路径重复提取文件名。多个不同名新文件的这一段工作近似 O(n²)。现在按需创建本轮 `basename → 有序 Set<path>`，只查询同名候选；没有新路径的正常扫描不构建索引。

保留原行为：

- 原路径仍存在时不抢占其游标；大小写不敏感的文件名匹配不变。
- 多个同名旧路径按原游标插入顺序查找，并逐次检查路径是否仍存在。
- 本轮新增、迁移、重建的游标同步维护索引；索引不跨轮持有过时的文件存在状态。
- 归档迁移后只统计新增行；截断仍初始化到当前大小，不重新计算已入账历史。
- 不改变原子 JSON 快照写盘方式，没有延迟写盘或丢弃历史。

“近似线性”仅指不同名文件的游标候选搜索，不是整个同步流程的复杂度保证。如果很多候选真的同名，仍须按顺序逐个核对路径存在性。

## 前后对照

运行：`node scripts/benchmark-usage-cursor-index.js`。原始样本见 `PERFORMANCE-CURSOR-INDEX-2026-09-16.json`。

2026-09-16 17:07:29（Asia/Shanghai），Windows x64，Node v22.22.3，AMD Ryzen 5 7520U。对照固定提交 `42c62ea` 的 `lib/codex-usage.js`，优化版为当前工作区。基线在同一 JavaScript realm 编译，使用相同 fs/path、同一套刚写入的合成文件；每组 3 次，基线/优化版交替先后顺序。没有清空系统文件缓存，机器不是独占测试环境。

每个合成账号有 100、1000、2000 个不同名 JSONL，各含一个 1000 输入/900 缓存/100 输出的 token 事件。测试真实目录扫描、真实解析和真实原子快照写入；每次断言请求数、输入、缓存、输出与游标数完全匹配。

三个路径：首次空游标同步；强制到期但文件未变化；保留已计费游标而把旧路径替换为不存在的同名路径，再扫描现有文件，模拟整批历史路径迁移。后者断言所有游标转到实际存在的路径，且历史统计不增加。不是 UI/HTTP 端到端量测，也不模拟 365 天聚合账本。

| 文件数 | 首次：原版 | 首次：索引版 | 迁移：原版 | 迁移：索引版 | 未变：原版 | 未变：索引版 |

本机该组 2000 文件首次同步中位数下降约 60.1%，迁移下降约 69.3%。这是合成样本结果，不是全机型承诺。100 文件迁移并未变快；未变化路径没有目标算法改动，其计时差异不应宣称为索引收益。样本中存在明显后台负载/文件系统调度波动，例如索引版 2000 文件迁移为 468.003、1002.580、362.601ms。

独立于计时再做计数（插桩不进入上表）：128 个新文件的全部 `path.basename` 调用从 **8640 次降到 640 次**。回归测试还直接观察 64 文件的游标对象枚举：**只 2 次（建索引 + JSON 快照）**，不再每文件一次；后续未变化强制同步为 **0 次**。这比单纯的耗时波动更直接地证明重复搜索已消除。

脚本只操作 `mkdtempSync` 创建的专属 Temp 子目录，单次写入硬上限 50 MB，正式对照实际逻辑写入 18,918,756 字节，完成后已清理。此前跨 realm 版本做过一次方法校准（同样 18,918,756 字节），没有将其计时混入正式结果；两次合计 37,837,512 字节。无真实账号、凭证或账本读取，无模型请求、网络、CLI、server 启动、进程结束或更新安装。
